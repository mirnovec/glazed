# Task: seed-based overworld ore ESP for the Glazed Meteor addon

Build an overworld counterpart to the existing `netherite-finder` module: predict ore positions
from the world seed and draw them as ESP boxes with tracers. Priority target is **deepslate
emerald ore**, but it must work for every overworld ore (diamond, gold, iron, coal, redstone,
lapis, copper, emerald).

Server is **DonutSMP**, Minecraft **26.1.2**, Meteor addon source at `/home/ilija/glazed-src`.
Normal xray does not work there — the server runs anti-xray, which is the whole reason for the
seed approach.

---

## What already exists — reuse it, do not rewrite

A working nether version is already in the repo and is ~90% of this job:

| File | What it does |
|---|---|
| `src/main/java/com/nnpg/glazed/modules/esp/NetheriteFinder.java` | module: per-chunk simulation, ESP boxes, tracers, air/target filters, diagnostics |
| `src/main/java/com/nnpg/glazed/utils/NetherOre.java` | builds the ore table from vanilla data, computes feature indices |
| `src/main/java/com/nnpg/glazed/mixins/{CountPlacement,HeightRangePlacement,RarityFilter}Accessor.java` | read private placement fields |
| `src/main/java/com/nnpg/glazed/commands/DebrisCommand.java` | `.debris` / `.debris verify` / `.debris scan` diagnostics |

The core loop, already proven correct against vanilla:

```java
WorldgenRandom random = new WorldgenRandom(WorldgenRandom.Algorithm.XOROSHIRO.newInstance(0));
long populationSeed = random.setDecorationSeed(seed, chunkMinX, chunkMinZ);
random.setFeatureSeed(populationSeed, ore.index, ore.step);
int repeat = ore.count.sample(random);
for (int i = 0; i < repeat; i++) {
    if (ore.rarity != 1 && random.nextFloat() >= 1.0f / ore.rarity) continue;
    int x = random.nextInt(16) + chunkMinX;
    int z = random.nextInt(16) + chunkMinZ;
    int y = ore.heightProvider.sample(random, ore.heightContext);
    // biome filter, then vanilla OreFeature / ScatteredOreFeature vein walk
}
```

**Do not simulate terrain** for chunks the client has. Compute candidate positions from the seed,
then filter against the real client world. That was verified to work: quartz/gold predictions
matched **905 of 907** visible ore blocks (1.2% chance baseline).

For chunks the client does *not* have, there is nothing to filter against, so `utils/SeedWorld`
runs vanilla's own `BiomeSource` and `NoiseBasedChunkGenerator` off the seed to answer the only two
questions the simulation needs: which biome, and how high is the terrain (`OCEAN_FLOOR_WG`). That
is behind the `predict-unloaded` setting and is strictly a fallback — a chunk arriving throws the
guess away and re-simulates it against real blocks. Caves are still not simulated, so predictions
in unloaded chunks over-report: ore predicted inside a cave never generated.

## Critical technique: verify with blocks anti-xray does not hide

DonutSMP hides buried ore. Measured in the nether: **877 exposed ore blocks vs 2 buried**, and
zero visible ancient debris across 81 chunks. So you can never confirm an ore prediction against
client block data.

But anti-xray only hides **ores**. These are generated by the same `UNDERGROUND_ORES` pipeline and
are sent truthfully even when buried, which makes them perfect no-mining ground truth:

| Feature | Index | Size | Notes |
|---|---|---|---|
| `ORE_DIRT` | 0 | 33 | count 7, y 0..160 |
| `ORE_GRAVEL` | 1 | 33 | count 14, full height |
| `ORE_GRANITE_UPPER` / `LOWER` | 2 / 3 | 64 | huge blobs, thousands of blocks |
| `ORE_DIORITE_UPPER` / `LOWER` | 4 / 5 | 64 | |
| `ORE_ANDESITE_UPPER` / `LOWER` | 6 / 7 | 64 | |
| `ORE_TUFF` | 8 | 64 | y bottom..0 |
| `ORE_CLAY` | 27 | 33 | count 46 |

**Port `.debris verify` and `.debris scan` first, before writing any rendering.** They give a
verdict in seconds with zero mining:

- `verify` — counts how many visible reference blocks the predictions hit vs a chance baseline.
  Expect >90% vs a ~1-3% baseline if the seed is right.
- `scan` — brute-forces indices 0..40 per ore and reports which index actually matches reality.
  Detects any ordering shift immediately.

Known reporting bug to fix when porting `scan`: it labels rows by ore *type*, so two variants of
the same ore (e.g. upper/lower granite) both print and the one that does not generate locally
looks "SHIFTED". Label rows by **feature name**, not type.

## Overworld generation data (extracted from the 26.1.2 client jar — trust these)

Generation step is **`UNDERGROUND_ORES` = ordinal 6**, with **34 features** at that step.
Height context: `LevelHeightAccessor.create(-64, 384)` → minGenY -64, genDepth 384.

### Emerald — the priority target

```
ORE_EMERALD  index=33  size=3  discardChanceOnAirExposure=0.0  scattered=false
             count=100  rarity=1  height=triangle(-16, 480)
             targets=[emerald_ore, deepslate_emerald_ore]
```

Four things matter here:

1. **`discardChanceOnAirExposure = 0.0`** — no air-exposure discard at all. This is the single
   biggest reason emerald is a better target than ancient debris was: no fragile filter, the
   prediction is just "position + target block matches".
2. **Only 10 of 54 biomes generate it**: `snowy_slopes`, `windswept_gravelly_hills`, `grove`,
   `windswept_hills`, `windswept_forest`, `meadow`, `jagged_peaks`, `stony_peaks`,
   `cherry_grove`, `frozen_peaks`. The biome filter is essential or you will predict emerald
   across the whole map.
3. **`deepslate_emerald_ore` is the same feature** — the ore picks its block from the target it
   replaces (stone → `emerald_ore`, deepslate → `deepslate_emerald_ore`). There is no separate
   deepslate feature to look up.
4. **Deepslate emerald is genuinely rare.** The triangle peaks at y≈232 and deepslate only exists
   below y≈0, so deepslate emerald sits in the extreme bottom tail of the distribution *and*
   requires a mountain biome. Set expectations accordingly — surface emerald at high y in
   mountains will be vastly more common.

## The big risk: Paper per-feature seeds

The nether attempt died here, so check for it **early** rather than after building everything.

Paper lets a server override the population seed of a single feature
(`paper-world-defaults.yml` → `feature-seeds`):

```java
long featurePopulationSeed = decorationSeed;
final long configFeatureSeed = level.getMinecraftWorld().paperConfig()
        .featureSeeds.features.getLong(feature.feature());
if (configFeatureSeed != -1) {
    featurePopulationSeed = random.setDecorationSeed(configFeatureSeed, origin.getX(), origin.getZ());
}
random.setFeatureSeed(featurePopulationSeed, globalIndexOfFeature, stepIndex);
```

Set on one feature, that feature's positions become unpredictable while **every other ore stays
perfectly vanilla**. This is exactly what was measured in the nether: quartz 99.6%, gold 99.4%,
blackstone 97%, magma and gravel exact, **ancient debris 0%**. DonutSMP almost certainly does this
for its high-value ores, and **diamond and emerald are the obvious overworld candidates.**

**Detection (no mining):** run the visible-block verify. If dirt/gravel/granite/diorite/andesite
all verify but diamond and emerald cannot be confirmed, a per-feature seed is the likely cause.

**If it is happening**, a cracker already exists and is self-tested:
`/tmp/.../scratchpad/idxtest/DebrisCrack.java` (adapt the ore params). It recovers the hidden seed
at **8.9M seeds/sec** on this machine:

- under 2³² (any human-chosen number) → ~8 minutes
- up to 2⁴⁰ → ~34 hours
- full random 64-bit → not feasible, say so and stop

It needs **3+ real ore positions in different chunks**. Same-vein blocks are correlated and count
as roughly one observation.

## API gotchas already hit and solved on 26.1.2 — do not rediscover these

- 26.x ships **unobfuscated**; mappings are `loom.officialMojangMappings()`. Verify any uncertain
  API with `javap` against
  `/home/ilija/.local/share/PrismLauncher/libraries/com/mojang/minecraft/26.1.2/minecraft-26.1.2-client.jar`
  rather than guessing.
- **`new WorldGenerationContext(null, heights)` throws NPE on 26.1.2** — it dereferences the
  generator. Pass the real `ChunkGenerator` from the `LevelStem`.
- **`ChunkPos` is a record**: use `.x()`, `.z()`, `ChunkPos.pack(...)`, `chunk.getPos().pack()`.
  `.asLong()` / `.toLong()` do not exist.
- Vanilla's `Feature.isAdjacentToAir` tests **`BlockState.isAir()`**, not `!canOcclude()`. Using
  `canOcclude` wrongly treats lava and non-full blocks as exposure.
- **Implement the target `RuleTest`.** Ores only replace specific blocks (`stone_ore_replaceables`
  / `deepslate_ore_replaceables` tags in the overworld). Skipping this produced large numbers of
  false positives in the nether version.
- `RarityFilter.chance` is an **`int`** on 26.1.2 (older references treat it as float).
- `VanillaRegistries.createLookup()` takes ~1s — run it off-thread and pass `minY`/`logicalHeight`
  in as parameters rather than reading the level from another thread.
- Cache per chunk, but **do not cache a chunk whose neighbours are not loaded yet** — edge lookups
  return air and permanently poison the result. Retry on a periodic sweep.
- Never scan the whole loaded area every tick. Gate expensive sweeps to ~40 ticks; a full-radius
  per-tick scan is millions of block lookups per second.

## Suggested order

1. Port `NetherOre` → `OverworldOre` (step 6, overworld `LevelStem`, overworld height context).
2. Port the **verify + scan diagnostics first**, and confirm the seed works in the overworld using
   granite/diorite/andesite/dirt/gravel. Do not build rendering until this passes.
3. Run scan on diamond and emerald. If the visible blocks verify but these do not, suspect
   per-feature seeds and go to the cracker rather than tuning filters.
4. Only then build the ESP module: boxes + tracers, per-ore toggles and colours, `min-y`/`max-y`,
   `max-distance`, `chunk-range`, `nearest-only` tracer.
5. Default emerald on, everything else off; keep the visible-block ores available as a built-in
   seed self-test.

## Lesson from the nether attempt — please respect this

Every prediction filter was tuned three separate times against a world that had been mined out and
obfuscated, and none of it mattered, because the real problem was a server config. **Get a
quantitative ground-truth measurement before writing or tuning any filter.** The visible-block
verify gives that in seconds and needs no mining. If a measurement and a theory disagree, the
theory is wrong.
